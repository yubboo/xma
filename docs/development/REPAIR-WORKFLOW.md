# XMA 修复工作流

> 本文定义 XMA 的 Bug/回归修复留痕合同。修复不是一次性聊天动作，而是可复查、可重放、可验证的工程记录。

## 1. 为什么需要独立修复工作流

XMA 同时包含 Runtime、Terminal、Desktop、Web、Windows 开发链、Native Kernel 等多个域。局部修复如果只依赖即时上下文，容易出现：

- 修复 A 时无意破坏已经验收的 B；
- 同一个问题被重复猜测、重复打补丁；
- 修复依据、上游参考和验收条件只存在于聊天中；
- 后续开发者不知道“为什么这样写”，误删防回归约束；
- 源码、文档、测试和发行包状态不一致。

因此，从本规则生效后，所有非纯文案 Bug 修复都必须先建立编号修复 Prompt，再实施代码修改。

## 2. 权威文件分工

| 文件 | 职责 |
| --- | --- |
| `docs/development/REPAIR-PROMPTS.md` | 按 `# 01 / # 02 / ...` 保存每次修复的原始问题、根因证据、修复 Prompt、验收条件、结果和残留优化项。 |
| `docs/development/UPDATE-LOG.md` | 保存已经完成的历史变更摘要；完成修复后必须增加对应记录。 |
| `docs/development/PROJECT-STATUS.md` | 保存当前真实开发状态、当前阻塞、待优化项与下一开发批次。 |
| `docs/development/DEVELOPMENT-PLAN.md` | 保存中长期路线；只有修复改变路线/阶段时才更新，禁止把短期 Bug 清单塞进长期计划。 |
| `AGENTS.md` / `DEVELOPMENT-RULES.md` | 保存已经证明必须长期遵守的防回归硬规则。 |

禁止在多个文件复制完整同一份修复正文。`REPAIR-PROMPTS.md` 是修复上下文第一事实源，其余文档只保存各自层级需要的摘要和规则。

## 3. 编号和标题

修复条目使用连续编号：

```text
# 01 Terminal 历史滚动、光标稳定与启动链回归
# 02 Provider 配置保存失败
# 03 Desktop Approval 状态不同步
```

规则：

1. 两位数字起步，达到 100 后自然扩展为三位；编号不得复用。
2. 标题必须说明“修复什么”，不能写 `杂项修复`、`Bugfix`、`继续优化`。
3. 一个编号可以覆盖同一根因簇中的多个症状；不同根因应拆成不同编号。
4. 已完成条目不得改写历史结论；后续发现新根因，用新编号补充并引用旧编号。
5. **编号冲突自动顺延**：用户、开发者或外部任务如果口头指定了一个已经存在的编号，不得覆盖该历史；应自动选择当前下一个未占用编号，并在新条目中记录“用户原提议编号 → 实际编号”的原因。不得要求用户先记住历史编号才能继续工作。
6. 已有业务模块（例如 #05 Metrics）后续只做 UI/Host 投影优化时，必须在新 Repair 条目中引用原编号作为来源，但新问题仍使用新的不可变 Repair ID。

## 4. 修复前必须填写

每个条目在改代码前至少包含：

- 状态：`调查中 / 实施中 / 验证中 / 已完成 / 阻塞`；
- 日期；
- 用户可见症状；
- 已确认事实与证据；
- 明确排除项；
- 根因假设或已经确认的根因；
- 上游/官方实现参考；
- **可直接交给下一位开发者/智能体执行的修复 Prompt**；
- 不允许回归的既有行为；
- 验收条件。

如果根因还没确认，Prompt 必须要求“先验证再修改”，禁止把猜测写成事实。

## 5. 实施规则

1. 优先修根因，不在表现层无限叠补丁。
2. 单个 Host 文件同时拥有布局、输入、动画、滚动、业务状态等多个高耦合域时，必须先评估模块拆分；Bug 修复不得继续扩大巨型文件。
3. UI Host 只修 UI/交互；Agent Runtime、Provider、Tool、安全策略继续遵守各自 ownership。
4. 对成熟基础能力，按 Upstream-first 查官方源码/测试；记录“吸收了什么、没有照搬什么”。
5. 修复必须补可失败的回归测试，不能只增加“源码里出现某字符串”的弱静态断言来冒充行为验证。
6. 无法在当前环境执行的 E2E 必须明确标记，禁止宣称已经实机验证。

## 6. 完成后必须回填

条目进入 `已完成` 前必须增加：

- 最终根因；
- 实际修改文件/模块；
- 回归测试与 Gate 结果；
- 实机仍需验收的项目；
- 对应 `UPDATE-LOG` 编号/摘要；
- 残留风险；
- 待优化进度（如果有）；
- 下一步。

同时：

- 如果形成长期防回归原则，更新 `AGENTS.md` / `DEVELOPMENT-RULES.md`；
- 如果改变当前开发状态，更新 `PROJECT-STATUS.md`；
- 如果改变长期路线，才更新 `DEVELOPMENT-PLAN.md`；
- 重新生成 Source Manifest 和正式源码包后，再把发行校验结果写入条目。

## 7. 修复完成定义（Definition of Done）

一个修复只有同时满足以下条件才能标记“已完成”：

1. 根因有证据，不是猜测；
2. 修复落在正确 ownership；
3. 已有正常行为没有被顺手改坏；
4. 回归测试覆盖本次故障路径；
5. 项目 Gate 通过，或明确记录不能运行的原因；
6. 文档/状态/历史完成同步；
7. 最终源码包与 Source Manifest 一致；
8. 对需要 Windows Terminal、真实 Provider、Desktop GUI 等实机条件的项目，明确列出尚待用户 E2E 的验收项。

## 8. 禁止事项

- 禁止“先改完再补一段看起来合理的 Prompt”伪造过程；Prompt 应在主要代码修改前建立。
- 禁止为了让测试通过而把测试改成只匹配实现字符串。
- 禁止因为一个 UI Bug 顺手改 Agent Runtime/Provider 语义。
- 禁止把用户实机仍失败的问题继续描述为“已经修复完成”。
- 禁止删除历史失败尝试；应在对应条目中记录“尝试过但被证伪”的方案，避免重复踩坑。
